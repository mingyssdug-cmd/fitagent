## 1. 项目背景

### 1.1 问题定义

个人健身者在制定训练和饮食计划时，面临三个问题：

1. **知识门槛高**：需要了解 BMR/TDEE 计算、宏量营养素分配、动作规范，普通人没有这些知识
2. **方案不个性化**：网上的通用模板不考虑个人体重、目标、活动水平、伤病史
3. **难以坚持与调整**：计划是静态的，无法根据执行反馈动态调整

### 1.2 项目目标

构建一个**个人健身助手 Agent**，用户填写基础信息后，系统自动生成个性化的训练计划和饮食计划，并支持多轮调整。

**核心价值**：
- 把"专业教练的决策流程"产品化
- 所有数字来自确定性计算，所有建议来自可追溯的知识库
- 用户可以在生成后要求调整，直到满意

### 1.3 项目边界

**做什么（v1.0）**：
- 用户注册/登录（手机号 + 密码）
- 填写个人档案（性别、年龄、体重、身高、活动水平、目标、伤病史）
- 生成训练计划（周结构、动作、组数次数）
- 生成饮食计划（热量、宏量营养素、餐次分配）
- 用户确认或要求重新生成
- 保存历史计划，支持查看

**不做什么（v1.0）**：
- 会员打卡、体重记录、进度追踪
- 社交功能（分享、评论、点赞）
- 付费订阅
- 与运动手环/健康 App 的数据同步
- 前端界面（只提供 API + Swagger 文档）

### 1.4 与上一版的区别

本版是**工程化重构**，不是功能重做。与上一版（健身工作室智能体）的区别：

| 维度 | 上一版 | 本版 |
|---|---|---|
| 用户模型 | 教练 + 会员（两个角色） | 个人用户（单角色） |
| 核心流程 | 教练录入 → AI 生成 → 教练审核 | 用户填写 → AI 生成 → 用户确认 |
| 数据模型 | members + plan_history | users + plans |
| 项目结构 | main.py 单文件，无分层 | 四层架构（API → Service → Agent → Data） |
| 接口规范 | 无 | OpenAPI 3.0 规范 |
| 部署 | 本机跑通 | 本机跑通（Docker 留作后续迭代） |

**本版的核心目标是"工程化"**：分层清晰、可维护、可扩展、有文档。

## 2. 用户角色

v1.0 只有一个角色：**个人用户**。

| 属性 | 说明 |
|---|---|
| 身份 | 想制定健身饮食计划的个人 |
| 特征 | 有基础健身知识或完全没有，希望系统给出专业建议 |
| 核心诉求 | 快速拿到个性化的、可执行的计划 |
| 使用场景 | 手机上填写信息，几秒后拿到计划 |

**不做角色区分**：v1.0 不区分"新手/老手"、"学员/教练"。所有用户都是同一角色，只是填写的档案不同。

## 3. 核心业务流程

### 3.1 主流程
用户注册
↓
用户登录（拿到 JWT token）
↓
用户填写/更新个人档案
↓
用户发起"生成计划"请求
↓
系统并行执行：
├── 计算 BMR / TDEE / 宏量营养素
├── 检索营养知识库（餐次分配、食物选择）
└── 检索动作知识库（动作规范、禁忌）
↓
LLM 编排生成营养计划 + 训练计划
↓
系统暂停，等待用户确认（HITL 中断点）
↓
用户确认 → 保存计划到历史 → 返回最终结果
用户要求调整 → 带反馈重新生成 → 再次等待确认

### 3.2 异常流程

**流程 A：热量低于安全阈值**
- 系统检测到生成的热量 < 1200 kcal
- 拦截输出，返回警告："计划热量低于安全下限，请调整目标或咨询专业人士"
- 不保存到历史

**流程 B：用户档案不完整**
- 用户发起生成请求，但档案缺少必要字段（如体重、身高）
- 返回 400 错误，提示缺少哪些字段

**流程 C：用户要求调整**
- 用户在确认环节输入修改意见（如"蛋白质太少"）
- 系统带反馈重新生成
- 再次进入确认环节
- 循环直到用户确认或达到最大重试次数（3 次）

**流程 D：知识库检索为空**
- 检索营养库或动作库返回空结果
- 系统仍能生成计划，但提示"未找到相关知识库依据，建议仅供参考"

## 4. 功能需求

### 4.1 用户认证

| 功能 | 说明 |
|---|---|
| 注册 | 手机号（11 位）+ 密码（≥6 位）+ 姓名 |
| 登录 | 手机号 + 密码，返回 JWT token |
| token 校验 | 所有业务接口需要 Bearer token |

**密码存储**：bcrypt 哈希，不存明文。
**token 有效期**：24 小时。

### 4.2 用户档案管理

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| name | string | 是 | 姓名 |
| gender | string | 是 | male / female |
| age | int | 是 | 年龄 |
| weight_kg | float | 是 | 体重（公斤） |
| height_cm | float | 是 | 身高（厘米） |
| activity | string | 是 | sedentary / light / moderate / active / very_active |
| goal | string | 是 | cut（减脂）/ bulk（增肌）/ maintain（维持） |
| experience | string | 是 | beginner / intermediate / advanced |
| injuries | string | 否 | 伤病史，如"肩关节损伤" |
| days_per_week | int | 是 | 每周可训练天数 |

| 接口 | 说明 |
|---|---|
| GET /users/me | 获取当前用户档案 |
| PUT /users/me | 更新当前用户档案 |

### 4.3 计划生成

| 接口 | 说明 |
|---|---|
| POST /plans/generate | 生成计划，返回两份计划和中断状态 |
| POST /plans/{plan_id}/confirm | 确认计划（用户通过） |
| POST /plans/{plan_id}/revise | 提交修改意见，触发重生成 |
| GET /plans | 查询历史计划列表 |
| GET /plans/{plan_id} | 查询单个计划详情 |

**生成的计划包含**：
- 营养计划：目标热量、宏量营养素、餐次分配、食物示例
- 训练计划：周结构、每日动作、组数次数、组间休息、替代动作

### 4.4 知识库检索

| 知识库 | 内容 | 用途 |
|---|---|---|
| 营养库 | 热量计算原则、宏量分配、餐次建议、食物数据 | 生成饮食计划时检索 |
| 动作库 | 动作规范、目标肌群、禁忌、替代动作 | 生成训练计划时检索 |

**检索结果必须带来源**（文档名 + 页码），供用户追溯。

### 4.5 安全护栏

| 护栏 | 触发条件 | 行为 |
|---|---|---|
| 热量下限 | 生成热量 < 1200 kcal | 拦截，返回警告 |
| 禁忌动作 | 计划包含用户伤病史对应的禁忌动作 | 拦截，要求重新生成 |
| 输出格式 | 计划结构不完整 | 拦截，要求重新生成 |

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 响应时间 | 单次计划生成 < 60 秒（含 LLM 调用和 RAG 检索） |
| 并发 | 支持 10 个用户同时请求 |
| 数据持久化 | 用户档案、历史计划永久保存 |
| 会话持久化 | 支持中断后恢复（用 LangGraph checkpointer） |
| 可追溯 | 每个计划记录生成时间、使用的知识库版本 |
| 日志 | 所有 API 请求记录访问日志，错误记录完整堆栈 |
| 安全 | 密码哈希存储、JWT 认证、SQL 注入防护（ORM 天然支持） |
| 可维护性 | 四层架构，每层职责单一，依赖注入 |
| 可测试性 | 核心业务逻辑有单元测试，覆盖率 > 60% |

## 6. 关键设计决策

> 这一节是本文档的核心。每条决策都要回答“为什么这么做”，作为后续代码的依据。

### 决策 1：为什么用四层架构（API → Service → Agent → Data）

**问题**：上一版把路由、业务逻辑、数据库操作都写在 `main.py` 里，导致文件臃肿、无法复用、无法测试。

**方案**：
- **API 层**：只做 HTTP 转接（解析请求、调用 Service、返回响应）
- **Service 层**：编排业务逻辑（调用 Agent、调用 Repository）
- **Agent 层**：定义智能体、工具、提示词
- **Data 层**：数据库读写、向量库读写

**原则**：每层只能调下一层，不能反向调用，不能跨层。

**收益**：
- 改数据库不影响 Agent 逻辑
- 改 Agent 不影响 API 定义
- 每层可以独立测试

### 决策 2：为什么 BMR/TDEE/宏量营养素必须用工具算

**问题**：LLM 是概率模型，同样输入可能给不同输出。健康类应用必须可审计、可复现。

**方案**：所有数学计算下沉到 `app/tools/calculator.py`，LLM 只能调用工具，不能自己算。

**收益**：同样的用户档案，任何时候生成的目标热量都完全一致。

### 决策 3：为什么营养和训练拆成两个 Agent

**问题**：营养和训练的领域知识差异大，提示词约束不同。

**方案**：
- `agents/nutrition.py`：营养 Agent，带计算工具 + 营养库检索
- `agents/workout.py`：训练 Agent，带动作库检索
- `agents/graph.py`：用 LangGraph 编排两个 Agent

**收益**：各自的提示词更聚焦，中间件更干净，未来可以独立迭代。

### 决策 4：为什么用 HITL（人在环路）

**问题**：LLM 生成的计划不一定符合用户预期。直接返回给用户，用户可能不满意。

**方案**：生成后在 `review_node` 用 `interrupt()` 暂停，等用户确认或反馈。

**收益**：
- 用户有控制权
- 反馈能触发重生成，逐步逼近用户预期
- 状态持久化，用户可以在任意时间回来确认

### 决策 5：为什么 RAG 检索结果要带来源

**问题**：健康建议如果出错，后果严重。用户无法判断 AI 说的对不对。

**方案**：检索结果格式化时带上 `[来源 X | 第 Y 页]`。

**收益**：
- 用户可以追溯依据
- 出错时能定位是知识库问题还是模型问题

### 决策 6：为什么数据模型用 users + plans，而不是上一版的 members + plan_history

**问题**：v1.0 是 To C 场景，只有一个角色，不需要"教练-会员"两层结构。

**方案**：
- `users` 表：存用户档案
- `plans` 表：存历史计划，外键关联 users

**收益**：数据模型更扁平，查询更简单。

### 决策 7：为什么用 JWT 而不是 Session

**问题**：API 服务需要无状态认证，方便水平扩展。

**方案**：登录后返回 JWT token，客户端每次请求带 `Authorization: Bearer <token>`。

**收益**：服务端不存 session，无状态，方便后续加负载均衡。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| BMR | 基础代谢率，身体静息状态消耗的最低热量 |
| TDEE | 每日总消耗，BMR × 活动系数 |
| 宏量营养素 | 蛋白质、脂肪、碳水化合物 |
| cut | 减脂 |
| bulk | 增肌 |
| maintain | 维持体重 |
| HITL | Human-in-the-loop，人在环路 |
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| Agent | 能自主决策、调用工具的 LLM 应用 |
